## 1. Stopping rules (never relaxed)
- Nothing lands on `main`, deploys (`deploy-app.yml`, Vercel), applies infrastructure, or touches a secret, Parameter Store value, Vercel variable, vendor console or the production database without the owner's explicit yes in chat for that action. A deploy that rolls the voice service also needs his word that no call is running or planned.
- Never set `HEALDESK_DIRECT_BOOKING_ENABLED`, `voice_real_calls`, `voice_provision_enabled`, `HEALDESK_PHASE_TWO_ATTRIBUTION`; never set `approvedByCounsel: true`; never move a `LAUNCH_PROMISES` item to `on` without production evidence and the owner's word.
- PHI boundary: the portal is `apps/app` (BAA host, synthetic data only until the BAA chain is complete). `apps/web` has no database client. No `@vercel/*`, no edge runtime in `apps/app`. No secrets, PHI or signed agreements in Git or PR text.
- The portal's permanent limits (CLAUDE.md): six screens (Home, Settings, Knowledge, Conversations, Bookings, Billing), nothing nested more than one level deep, Settings holds every switch on one page in cards. It must never grow prompt or script editing, a flow builder, per-channel behaviour differences, a live staff inbox, outbound campaigns, raw analytics dashboards, immediate in-app cancellation, or direct calendar or EMR configuration. The booking mode (direct or staff-confirmed) is ONE clinic-wide choice, not per channel.
- No spending: no paid model runs, no live Stripe/Retell/Meta calls without the owner's yes.

## 2. Owner decisions (28 Oct 2026, in chat) that are already in the spec
- Both booking modes on every channel: direct booking for clinics that link their calendar, staff-confirmed (Auto-confirm off) for clinics that want a gatekeeper. Direct booking on Meta waits for DB-1 and a ruling on stating a time there; Meta takes booking requests until then.
- A new optional clinic setting, default off: after a call booking the agent offers to text the caller a hosted payment link, sent once, only if the caller agrees and reads the number back, fixed wording with no treatment or time. The owner says no counsel ruling is needed and treats it as approved. Toggle in onboarding and in Settings. It needs a connected payment gateway.
- A new optional setting: "What the assistant asks the patient to pay" = Deposit only (default) / Full payment, through the same hosted checkout and the clinic's own price list. Available only when a gateway is connected, the calendar is connected and Auto-confirm bookings is on. Turning any of those off returns it to Deposit only and tells the clinic why. Card numbers are never taken.
- Design: very minimal, Apple-like, plain toggles, a short motion explanation beside each setting that is greyed out or that changes another setting, saying why it is unavailable and what happens on and off. The page must work fully with the animation off.

## 3. What to build, in this order (propose a first useful slice to the owner, with what waits, before building the rest)
1. **A dependency model.** One pure, tested function (or module) that, from the clinic's state (gateway connected, calendar connected, auto-confirm, text registration status, channels bought), returns for every switch: enabled or not, the one-line reason when not, and what unlocks it. The server enforces it (a disabled switch cannot be set by a crafted request, and a change that breaks a dependency resets the dependent switch in the same transaction with an audit row and an in-portal notice). The UI and the animations only render what this module says. Never encode the rules twice.
2. **The settings redesign:** the Settings cards for Behaviour/booking/payments in the new look, built as a small reusable toggle and explanation component set. Motion: CSS/SVG or a small dependency-free library, respecting `prefers-reduced-motion`; no layout shift; keyboard and screen-reader operable (the explanation is real text first, the motion second); light and dark. Look for the existing design tokens before inventing any.
3. **The onboarding wizard step** for the same switches (behaviour step), so a clinic sets them at sign-up and can change them later.
4. **The payment-by-text and full-payment settings,** behind the dependency model, with the server paths. FIRST do a feasibility check and report it to the owner before writing any sending code: which route can send a text that is on the BAA chain (the clinic's gateway does not necessarily text a checkout link; do not assume it; an SMS sender must sign a BAA and needs per-clinic sender registration of one to four weeks). If no compliant route exists the setting ships greyed out with the true reason, and the owner decides. Sending is by the fixed tool layer only, never the model; idempotent; the 24-hour Meta rules are unaffected; no treatment name in anything sent or stored by the sender; the text is one per booking.
5. **Copy first, then the switch:** every client-facing sentence says "designed to"; add `LAUNCH_PROMISES` items (`apps/web/src/lib/admin/seo/launch.ts`) for payment-by-text and full payment in the commit that adds the promise; keep `/admin/map` (`apps/web/src/lib/admin/system-map.ts`, `key-presence.ts`) true.
6. **Further dashboard improvements,** each proposed to the owner before building: Home (what the assistant did, what needs attention), Bookings (requests awaiting staff, deposit pending), clearer channel status per channel (live / waiting for what), error and empty states.
