# Reading the AWS database without holding its credentials

Status: **proposed, nothing applied.** Written 22 October 2026 on the branch
`infra/db-access-plan`. Every step that changes AWS or GitHub is the owner's
(CLAUDE.md, "Mandatory stopping rules"). Task: the owner asked for a way for
Claude Code to see and change what is in the production database without the
owner doing it by hand each time.

## What stops it today

Read from `infra/aws`, not from notes:

- The instance is `publicly_accessible = false`, in the database subnet group, and
  its security group admits only the web service's tasks (`rds.tf`).
- ECS Exec is off on every service and the deploy role denies turning it on
  (`ecs.tf`, `iam.tf`); there is no bastion and IAM database sign-in is off.
- The master password lives in an RDS-managed Secret; the two working roles'
  passwords in Parameter Store, reachable only by task roles.
- `run-task.sh` deliberately never prints a task's output (a log can quote row
  values), and the repository is public, so anything a workflow prints is public.

Those are the design working, and none of it should be loosened. So the answer is
not a connection for Claude; it is a narrow, audited path that never puts a
credential in Claude's hands.

## The path

```
Claude  ── writes a query file, in a PR ──▶ owner reviews, merges, deploys (deploy-app.yml)
Claude  ── gh workflow run db-query.yml ──▶ owner approves in GitHub (environment db-query)
                                           ▼  OIDC: this repo, db-query env, main, owner's actor id
                              role healdesk-production-github-db-query
                                           ▼  ecs:RunTask on one family
                          task healdesk-production-db-query (no task role)
                                           ▼  secret READONLY_DATABASE_URL
                       role healdesk_readonly  ─▶  SELECT on 15 listed tables, read-only sessions
                                           ▼
                  CloudWatch log group /healdesk/production/db-query
Claude  ── aws logs … --profile healdesk-observer ◀── that log group only (SSO, 1 hour, MFA by owner)
```

What each piece is, and where it is:

| Piece | File |
| --- | --- |
| The queries: one SQL statement each, reviewed in git, fixed by the deployed commit | `apps/app/scripts/db-queries/*.sql` |
| The runner: name in, one JSON line out, read-only transaction, 200 rows, 30 s | `apps/app/scripts/db-query.ts` |
| The role's tables, and every table it is withheld from, with the reason | `apps/app/scripts/readonly-tables.ts` |
| The grants, rebuilt from that list on every migrate run | `apps/app/scripts/readonly-grants.ts` |
| The role and its attributes | `apps/app/scripts/provision-roles.sql` (only when `readonly_password` is passed) |
| Its password and URL, made inside AWS like the other two | `infra/aws/images/db-admin/entrypoint.sh`, `ssm.tf` |
| The task, its log group, its family | `ecs.tf`, `logs.tf`, `iam.tf` |
| The GitHub role | `infra/aws/db-query.tf` |
| Registering the task with a real image, and checking its shape | `.github/workflows/deploy-app.yml` |
| The approval-gated run | `.github/workflows/db-query.yml`, `infra/aws/scripts/run-task.sh db-query` |
| Claude's read window | `infra/aws/access/` |
| The guard: every table is on one of the two lists, or the build fails | `apps/app/tests/readonly-tables.test.ts` |

## Decisions, with the reason

1. **A dedicated read-only role, not the runtime role in a read-only transaction.**
   `healdesk_app` can read every patient table under row-level security; a SQL file
   could set the clinic and read a clinic's patients, and the output would land in a
   log Claude reads. Only a role that has no grant on those tables makes "no PHI" a
   property of the database rather than of reviewers' care.
2. **The allow-list is fail-closed.** Grants are revoked and re-granted from one list
   on every migrate run. A new table is unreadable until someone lists it, and the
   test fails until they decide. Of 89 tables on the day this was written, 15 are listed, 25 are patient tables,
   21 are credentials and sign-in, and 28 are **unreviewed** (withheld until read
   column by column).
3. **RunTask overrides are invisible to IAM, so the only family these roles may run
   is the one whose only secret is the read-only URL.** An override can replace a
   task's command. Run on `migrate`, that would be arbitrary SQL as the table owner,
   past every control here. The same is true of the existing deploy role, which is
   why it is pinned to main and the owner's actor. `deploy-app.yml` now refuses a
   `db-query` revision that carries any other secret.
4. **The approval is an environment reviewer, and not the only lock.** The deploy
   role's trust deliberately names no environment (`iam.tf`), so this is a second
   role whose subject names `db-query`. AWS still checks the repository, the ref
   and the actor. The environment's reviewer is one more lock; a GitHub setting
   cannot widen what the role may do.
5. **Output never touches the workflow log.** The repository is public. `run-task.sh`
   prints the task's ending and where its output is. Claude reads it from
   CloudWatch with the observer profile.
6. **The observer sees one log group.** Not `web`, `worker`, `voice` or the one-offs:
   `channels-link` prints a working single-use credential, and the others can carry
   what a clinic's patients said. An explicit Deny backs the missing Allow.

## What this does not give, and why

**No write path.** The owner asked for changes Claude can make directly. A write
role would need to be the table owner (bypasses row-level security, reaches every
patient row) or a role with UPDATE on listed tables, and the output of a write is
the thing most likely to quote a row. Until the owner decides which tables a write
role may touch, changes go the way they do now and stay reviewable:

- schema and data fixes are **migrations or reviewed scripts**, merged and run by
  `deploy-app.yml` (already main-only, owner-only, and checked for shape);
- one-offs for named patient-rights work stay the existing `run-task.sh` scripts.

If a write path is wanted, the shape that fits this design is a second family,
`db-apply`, running a reviewed `.sql` file as a role granted only the tables named
in a second list, behind its own environment with a reviewer, and printing only
row counts. It is a separate decision and a separate PR; nothing here prepares for
it beyond the pattern.

**No cross-clinic reads of tenant tables.** `healdesk_readonly` has no BYPASSRLS,
by design. A query on a table under row-level security needs a clinic id (the
workflow's `clinic` input). Cross-clinic aggregates would need BYPASSRLS, which is
exactly the attribute the role must never have. For counts across clinics, the
existing ops console (`/api/ops`) is the right surface.

## Rollout, in order (all owner steps)

1. Review `READONLY_TABLES` column by column. Move any you are unsure of to the
   withheld list. This is the one list that decides what Claude can read.
2. Merge this branch. `infra.yml` **apply** creates the two parameters, the
   log group, the task family, the GitHub role and the execution role's `readonly/*`
   read. (Without this, step 3's `bootstrap_db` fails fetching a parameter that does
   not exist.)
3. `deploy-app.yml` with `bootstrap_db` and `migrate`: db-bootstrap makes the
   password and URL and creates the role (and signs in as it); the migrate task
   then grants its tables; the deploy registers a `db-query` revision.
4. On GitHub: Settings, Environments, **New environment** `db-query`; Required
   reviewers: yourself; Deployment branches: **main only**.
5. In AWS: the permission set in `infra/aws/access/README.md`; on the Mac,
   `aws configure sso`.
6. First run: `db-query.yml` with query `migration-state`. It answers the question
   the earlier session could not (how far the host's migrations reach), from the log.

Standby treats the new role like the other two: the parameters stay, the instance
goes, and db-bootstrap signs in as the role again when the host comes back.

## Not checked

Nothing here has been run against AWS or a Postgres. What was run: the guard test
(3 pass), `tests` for the system map (36 pass), `sh -n` and `bash -n` on the shell
scripts, `run-task.sh`'s argument validation offline, the policies as JSON, the
workflows as YAML. What was **not**:

- `terraform validate`, `terraform test`, tflint and checkov are not installed on
  this machine; `infra.yml`'s plan job is the first thing that will read the `.tf`
  edits, and `tests/stack.tftest.hcl` may list the task families or secrets and
  need a line.
- psql's `\if :{?readonly_password}` guard (supported since PostgreSQL 10) is
  untested; CI and `dev-db.sh` call `provision-roles.sql` without the variable and
  must see the role skipped.
- Whether the observer role's `kms:Decrypt` condition is what CloudWatch needs to
  read a KMS-encrypted log group (AWS documents Decrypt for that; the exact
  context key has not been exercised). Step 6 shows it either way, and the fix, if
  needed, is in `observer.policy.json` alone.
- Whether `drizzle.__drizzle_migrations` is the journal's name on the host; it is
  drizzle-kit's default and `drizzle.config.ts` does not override it.
- Whether the existing policies on tenant tables return zero rows, or an error,
  for a role with no `app.clinic_id` set.
- That IAM Identity Center is enabled in the account.
